# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

DBuff is a Dota 2 match analytics backend built with Spring Boot 3.5, Java 21, and PostgreSQL 16. It fetches match data from the OpenDota API, stores player statistics, provides item/ability rankings, and integrates with Discord and OpenAI for match summaries.

## Build & Development Commands

```bash
# Build entire project
./gradlew build

# Run the server (requires PostgreSQL via docker-compose up -d)
./gradlew :server:bootRun

# Run all tests
./gradlew test

# Run a single test class
./gradlew :server:test --tests "com.ako.dbuff.SomeTestClass"

# Code formatting (Google Java Format via Spotless)
./gradlew spotlessCheck    # Check formatting
./gradlew spotlessApply    # Apply formatting

# Regenerate OpenDota API client from OpenAPI spec
./gradlew cleanupodtaClient generateDotapiClient
```

## Architecture

### Multi-Module Gradle Project

- **`server/`** — Main Spring Boot application (`com.ako.dbuff.DbuffApplication`)
- **`clients/dotapi/`** — Auto-generated OpenDota API client (OpenAPI Generator). Do not edit generated code directly; modify `clients/dota_api_formatted.json` and regenerate.

### Server Module Package Layout (`com.ako.dbuff`)

- `config/` — Spring configuration beans (caching, API clients, concurrency, Discord, OpenAI)
- `dao/model/` — JPA entities, `dao/repo/` — Spring Data repositories
- `resources/` — REST controllers and response models
- `service/` — Business logic:
  - `ai/` — OpenAI-powered match analysis and summarization
  - `constant/` — Hero/item/ability constants (cached from OpenDota)
  - `discord/` — Discord bot (JDA). `discord/command/` holds the command layer; see below.
  - `list/` — Match history scraping (Playwright + JSoup) and parsing
  - `match/` — Match processing, analysis, and detail mapping
  - `ranking/` — Item/ability ranking calculations
  - `instance/` — Instance configuration management

### Key Architectural Patterns

- **Virtual Threads (Java 21)**: Used throughout for high concurrency. HikariCP pool is 50 for local dev; the `prod` profile lowers it to 10 because Postgres is co-located on the same 2 GiB instance.
- **Semaphore-based concurrency control**: `ConcurrencyConfig` limits parallel match fetches (20) and page scrapes (5) to prevent resource exhaustion.
- **Rate limiting**: Guava `RateLimiter` on OpenDota API (60 req/min) and ScraperAPI calls.
- **Caching**: Caffeine + Spring Cache for hero/item/ability constants. Stored constants carry a schema version (`BaseApiConstantService.schemaVersion()`) and are refetched from OpenDota when the stored one is lower, keeping the old row if the fetch fails; `position_est` is stored only for matches mapped after it was added.
- **Schema management**: Hibernate `ddl-auto=update` owns the schema. There are SQL scripts in `server/src/main/resources/db/migration/`, but **Flyway is not on the classpath** — it was never added as a dependency, so those scripts have never run. Treat a `pg_dump` as the only authoritative schema, and do not assume a migration has been applied because a file exists. Indexes are declared with `@Index` on the entities so Hibernate owns them too; `V2__item_ranking_indexes.sql` is retained only as documentation of the `INCLUDE`/partial variants JPA cannot express.
- **Preview features are enabled**: `--enable-preview` is passed at compile time, to the test JVM, and in production (`template.yaml`). All three must agree — a class that actually uses a preview feature is marked in its class file and will not load on a JVM without the flag.

### Discord Command Layer

Commands do not touch JDA. Each implements `DbuffCommand` (name, JDA definition, `execute`) and talks to Discord only through `CommandContext`, which is why they are all testable against `FakeCommandContext` with no Discord connection.

- **`CommandRegistry`** is the single source of truth: both adapters dispatch through it, guild registration reads its definitions, and `/dbuff help` is generated from it, so help cannot drift from the implemented command set.
- **Two adapters, one handler per command.** `SlashCommandAdapter` serves `/` commands and autocomplete; `TextCommandAdapter` keeps the legacy text aliases (`!dbuf`, `!vs`, `!rerun`, `!retry` with the default prefix) working by mapping them onto the same option names. Never register a second listener for an input an adapter already handles — both surfaces see `!` messages and the command would be answered twice. The text prefix is `discord.commands.text-prefix` (env `DISCORD_COMMANDS_TEXT_PREFIX`, default `!`, 1-3 characters, no leading `/`), read through `TextCommandProperties` by the parser, adapter and help; a local test bot sharing a server with the production bot sets another one (e.g. `~`) so only it answers.
- **Validate, then acknowledge, then work.** Discord discards an interaction not acknowledged within 3 s, and an ephemeral message cannot carry a thread. So every handler does its cheap validation first with `replyEphemeral`, calls `acknowledge` second (which creates the thread), and does the slow work third, writing into the returned `AsyncReply`. Getting this order wrong means a typo produces a thread full of an error instead of a private correction.
- **Configuration changes are gated by Discord permissions, not a role list.** `DbuffConfigCommand` refuses `register`, `add`, `remove`, `link`, `modes` and `deactivate` unless `CommandContext.invokerCanManageChannel()` — Manage Server, or Manage Channel on the *parent* channel for a thread — and `status`/`help` stay open. The check is in `DiscordPermissions`, shared by all three contexts, and a handler's `FakeCommandContext` defaults to a manager so tests opt *in* to the refusal.
- **Servers are onboarded by `GuildLifecycleListener`, not only at startup.** `onReady` registers commands for guilds already joined; `onGuildJoin` registers them for a new one (via the shared `GuildCommandRegistrar`) and posts a welcome; `onGuildLeave` deactivates that guild's instances so their jobs stop failing against unreachable channels. `BotPermissions.REQUIRED` is the single list behind both the invite URL (logged at startup) and `ChannelReadinessService`, which `/dbuff register` uses to refuse a channel the bot cannot post or create threads in. `ChannelReadinessService` takes JDA `@Lazy` because JDA is built from the listeners that reach the command beans.
- **Re-registering a deactivated channel reactivates its instance.** `DbufInstanceConfigService.register` reuses the inactive row (replacing players and modes) and reschedules its jobs; only an *active* instance is rejected as a duplicate.
- **Registration imports history quietly.** `DbufInstanceConfigDomain.trackingSince` is set on register/reactivate; a player added later gets their own entry in `playerTrackingSince` (never a move of the instance-wide value, which would swallow the existing players' recent games), read through `trackingSinceFor`. In `LastMatchesProcessorService`, an unseen match whose *end* (start + duration, not start alone — a game in progress at registration is live news) is before the *earliest* cutoff of the tracked players who have it — so it is live if it is news to any of them — goes through `MatchProcessorService.process` with no parse request, thread or report, then one `sendBackfillNotice`. A null `trackingSince` (instances that predate the field) reports everything, as before. `RecentMatchesJob` is `@DisallowConcurrentExecution` because the first import can outlast the 5-minute trigger. New `MatchDomain` rows take `gameModeId` from the recent-matches response so the mode filter works on first sight; before, the null passed the filter and every mode was reported.
- **`player:` accepts more than the autocomplete ID.** `PlayerIdParser` reads an account ID, a Steam64 ID (offset `76561197960265728`) or an opendota/dotabuff/stratz/steam profile link, and `/dbuff register|add` reject the whole request naming any entry it cannot read rather than tracking the rest.
- **Players are keyed by name, so a clash never repoints an account.** `getOrCreatePlayer` looks up by account ID first; a name already used by a *different* account stores the newcomer as `"name (accountId)"`. Overwriting the existing row's ID would silently move another group's tracked player onto this account.
- **Per-channel settings are nullable, and null means "behave as before".** `InstanceSettings` is an `@Embeddable` on `DbufInstanceConfigDomain`. Hibernate loads an embedded object whose columns are all null as `null`, so code reads it through `effectiveSettings()`, never the field. Unset means AI on, `FULL` detail, the server-wide quiet window in the server's zone, and Ability Draft for `/stats` — so a channel that never touched `/dbuff settings` is unchanged. `InstanceSettingsApplier` is the one place values are parsed and validated; every rejection is an `IllegalArgumentException` written for the person who typed it, and the command shows it as is. The same applier serves REST via `UpdateInstanceRequest`.
- **Report detail is declared by each analyzer, not decided by the orchestrator.** `ReportAnalyzer.getMinimumDetail()` defaults to `FULL` so a new analyzer stays out of shorter reports until placed, and `isEnabledFor(settings)` lets one opt out of that rule — `AiSummaryReportHandler` answers to its own switch because it is the costly report. `MatchReportOrchestrator.enabledAnalyzers` is the single filter point for the partial, full and legacy paths; `analyzeMatch` (REST) is deliberately unfiltered. `ReportAnalyzerDetailTest` pins where each current analyzer sits.
- **Quiet hours are per channel.** `QuietHoursGuard.isQuietTime(InstanceSettings)` follows the server window when the channel chose nothing, never skips when it chose `off`, and reads its own window in the channel's timezone otherwise. Both `RecentMatchesJob` and `MatchParseCheckJob` ask with the instance's settings. A timezone alone also shifts the server window into that zone.
- **A channel's default game mode is a fallback, not a filter.** `GameModeResolver.resolveOrDefault(typed, channelDefault)` uses what the user typed, else the channel default, else Ability Draft. Registering with `mode:` seeds it so tracking and `/stats` agree. Stored as canonical constant names, which the resolver accepts back.
- **The statistics commands share `StatsRequestResolver`.** `/stats` and `/hero` both route their `player`/`hero`/`period`/`game_mode` validation through it, in that order, and get back a `StatsRequest` carrying the resolved date range, filters and footer label. It exists because two copies of the sequence above would drift, and the drift is silent: a handler that acknowledges before validating still works for every correct input. Option *names* are defined once in `StatsOptions` for the same reason — the resolver reads them by name, so a command spelling `game_mode` differently would compile, register, and then ignore what the user selected.
- **`player:` is optional and defaults to the channel's whole focus group.** The cap of `MAX_PLAYERS` (5) applies differently to each case, deliberately: explicitly named players over the cap are *rejected*, because the user chose them and dropping one would discard a choice without saying which; a focus group over the cap is *trimmed* so a bare `/stats` still answers, with `StatsRequest.omissionNotice()` stating "showing 5 of 8 tracked" in the acknowledgement. `PlayerReferenceResolver.focusGroup` sorts by name because the config stores players in a `Set` — without that, embed order and which player gets trimmed would both vary per invocation. Nothing caps group size at `/dbuff add` time, so a large group is possible; raise `MAX_PLAYERS` rather than removing the trim, since each player is another pass over the match history on a 2 GiB box.
- **Autocomplete providers** are keyed `command:subcommand:option`, most-specific-first — needed because e.g. `/dbuff add player:` searches all of OpenDota while `remove player:` must offer only tracked players. A provider serving the same option on several commands overrides `getCommandNames()` (e.g. `hero:` and `player:` mean the same thing on `/stats` and `/hero`); forgetting to gives the second command a silently empty picker, which `DiscordCommandWiringTest` now fails on. The OpenDota search provider has its **own** rate limiter and cache, deliberately separate from the 60 req/min match-fetch limiter, so typing in a picker cannot starve match ingestion.
- **Unknown names are reported, never dropped.** `ConstantNameResolver` and `GameModeResolver` return unresolved names and the services throw `UnknownConstantNameException`; silently discarding one turns a filtered query into an unfiltered top-N and answers a different question than the one asked.
- **Game mode defaults to Ability Draft.** `GameModeResolver` resolves the `game_mode:` filter against the OpenDota match-type dictionary — the same one `/dbuff` validates tracked modes against — with aliases `ability_draft`, `all_pick` and `all`, and accepts a comma-separated list. Two things to know: `all_pick` maps to **`game_mode_all_draft`** (22), because that is what the client labels All Pick, while `game_mode_all_pick` (1) is the unranked legacy mode; and the default lives in `resolveOrDefault`, used only by the command layer, so the REST API keeps treating "no mode given" as every mode rather than quietly narrowing.
- **A mode filter excludes matches with no recorded mode.** `MatchDomain.gameModeId` is null when the scraper could not map a mode name, and an `IN` predicate drops those rows. That is deliberate — an unknown mode is not Ability Draft — but it means the default filter hides such matches from `/stats` and `/hero`.
- **`trace_matches:` lists the games behind the numbers.** `MatchTraceReporter` posts `matchId - date` per player as a plain message after that player's embed, capped at `MAX_TRACED_MATCHES` with the overflow stated rather than elided. It goes through `PlayerStatisticRepository.findPlayerMatches`, which shares `buildMatchPredicates` with the aggregations on purpose — a trace built from a different predicate set would list games the numbers did not come from, which is worse than no trace. The combo subcommands pass their own `matchIds` instead, since those queries already know which games satisfied the conjunction. A trace failure is posted into the thread but never rethrown: the statistics are already out, and losing the trace must not lose them too.

### Replay pipeline (`service/replay/`)

Optional enrichment from Valve replays, off by default (`replay.processing.enabled`). Nothing in it may fail match ingestion or reports: every problem becomes a `ReplayStatus` on `ReplayParseRunDomain`.

- **One entry point, one replay at a time.** `ReplayProcessingJob` (Quartz, global, `@DisallowConcurrentExecution`) runs up to `replay.processing.batch-size` matches through `ReplayBatchService`, sequentially; `replayParseSemaphore` (`replay.processing.max-concurrent`, default 1) bounds parses on the 2 GiB host. The batch asks `ReplayQueue` for one match at a time, so a match that turns fresh mid-batch goes next (a running parse is not pre-empted).
- **Queue lanes, in order** (by `detailsMappedAt`, which must be set): (1) fresh matches, started and mapped within `fresh-window-hours` (6), and the due retries of those, newest match first; (2) due retries of matches mapped within `retry-priority-hours` (24) with at most `retry-priority-attempts` (2) attempts; (3) other new matches mapped within those 24 hours (including recently mapped old ones), newest first; (4) only when `replay.processing.backlog.enabled` (default false) and lanes 1-3 are empty: old retries (older or more attempts), then new matches mapped earlier than 24 hours ago, at most `backlog.batch-size` per job run, and only on cron-fired runs. Within a run a match is never taken twice. Priority is per match, not per instance.
- **A new replay triggers the job at once.** After the match is persisted with its replay location (`BasicMatchDetailsMapper`, `MatchDetailBackfillService`), `ReplayRequestAnnouncer` publishes `ReplayRequested`, but only for a match that started within the fresh window and passes `ReplayEligibility`, so a backfill of old matches does not trigger anything. `ReplayRequestListener` (after commit) triggers the replay job through Quartz when `replay.processing.enabled`, outside quiet hours and only when the job is not running and no manual trigger is pending; such a run carries `NO_BACKLOG`, so the backlog is left to cron-fired runs. The cron stays as the safety net. A replay Valve does not have yet is `FAILED_DOWNLOAD` with the usual backoff and stays in lane 1 while the match is fresh.
- **The game mode decides what runs** (`service/replay/mode/`). A `GameModeProfile` bean per mode (`AbilityDraftProfile` 18, with the 48-skill pool and 40 picks; `AllPickProfile` 22, `game_mode_all_draft`) and `GameModeRegistry`: a mode is processed only when it has a profile *and* is in `replay.processing.supported-modes`, which stays the switch (a configured mode with no profile logs a warning and is skipped). `ReplayRunService` resolves the profile once, hands it to `ReplayEligibility` (no active profile is `SKIPPED_NOT_SUPPORTED`) and to the parser, runs only the extractors whose `supports(mode)` is true and hands it to `ReplayAnalysisService`, and `ReplayReportService` posts only the sections that support it. `ReplayExtractor`, `ReplayAnalyzer` and `ReplayReportSection` default `supports(mode)` to true; `AbilityDraftExtractor` and `DraftSection` apply to Ability Draft only. `AbilityDraftExtractor` and `DraftSection` both decide through `AbilityDraftProfile`. The parser reads `m_AbilityDraftAbilities` through a `DraftReader` made by a `DraftReaderFactory` bean per mode in `clarity/` (`AbilityDraftReaderFactory`; `NoDraftReader` for other modes; the factory is not on the profile because readers use Clarity types), so a mode with a draft needs no change in `ClarityReplayParser`, and `ReplayFacts.draft` (`AbilityDraftFacts`) is null for All Pick, which writes no draft rows (its draft comes from OpenDota's `DraftEventDomain`; the replay has no pick stream for it). `ReplayAnalysisService.analyze` always takes the mode; the re-analysis endpoints get it from `StoredMatchModes` (a query for the mode id only): a single re-analysis of a match that is not stored or whose mode is inactive answers 409, and the bulk one counts it as `skipped`. `ReplayQueue` takes the modes for every lane (new matches and the three retry lanes) from `GameModeRegistry.activeModeIds()` (the same rule as `activeFor`) and hands out nothing when no mode is active. A new mode is a new profile bean plus its configuration entry.
- **Only `service/replay/clarity/` imports Clarity.** Extractors read `ReplayFacts`; a new table slice is a new `ReplayExtractor` bean, a new compression format a new `ReplayDecompressor` bean.
- **Identity is the roster, not the match id.** The replay's `m_unMatchID64` is a lobby id. `ReplayRosterVerifier` compares accounts per slot (hero for anonymous players); a mismatch is `FAILED_IDENTITY` and writes nothing.
- **Extractors store facts, not conclusions.** `AbilityDraftExtractor` writes the 40 picks and the 48-skill pool and stores nothing for a draft of another shape, rather than a partial one. The ability names come through the small `AbilityNames` interface, so the extractor does not depend on the constants cache.
- **Time is game time, not ticks.** A paused game keeps ticking, so `GameClock` takes the paused stretches (`m_bGamePaused`) out of every tick before it is used as a time; the combat log is stamped in game time already. Without it the samples of a match with pauses (one sample match has 218 s of them) drift away from the combat log by the length of each pause.
- **The parse reads the whole replay once** (about 1.4 s for a 45-minute game, at the 512 MB heap `replayTest` uses). `SampleRecorder` samples every player each 5 game seconds from the pre-game phase (-90 s) and their cumulative counters each minute; `ReplayTrackExtractor` and `ReplayMinuteExtractor` store them. Tracks are `int[]` columns (Hibernate maps them to SQL arrays natively; the hypersistence array types clash with Hibernate 6.6). Game states 8 and 10 occur before the pre-game phase, so "state at least 6" does not mean the game is over.
- **The hero-relevant combat log is stored as one zstd blob** (`ReplayCombatLogDomain`, laid out by `CombatLogCodec`, versioned) so that fights, deaths and swings can be recomputed after Valve deletes the replay. `CombatLogRecorder` keeps damage and deaths that involve a hero, hero ability and item uses, gold and experience, whitelisted modifiers on heroes, building kills and buybacks; analyzers read it through `CombatLogReader`. A combat-log death is not always a real death: an Aegis use is logged as one. The parse reads 10 s past the end of the game because the Ancient's fall is logged after the state changes.
- **Map positions are classified by `MapLayout`**, built from the buildings and camps the replay lists (`MapFacts`) and frozen as `replay/map-layout.json`, because the replay will be gone when an analysis runs. `MapLayouts.forVersion(run.mapVersion)` returns the layout only for the frozen map version, so a patch that moves a tower shows up as a missing layout instead of a wrong classification. A zone is a base, a lane (bottom, mid, top), the river or the jungle (with the camp when inside a camp box); its half says whose side of the river it is. The lane corridor, river and base sizes are in `MapLayout.Tuning`; they were checked against OpenDota's `lane` on two matches.
- **Analyzers work from stored data only.** A `ReplayAnalyzer` bean reads the extractors' tables, the combat-log blob and the frozen map, never the replay, and `ReplayAnalysisService` runs them after the extractors once the replay's facts are out of scope; a failing analyzer makes the run `PARTIAL`. Rows carry `analysisVersion`, so rules can change and be run again. Thresholds are in `ReplayAnalysisProperties` (`replay.analysis.*`). `ActivityAnalyzer` stores what each hero was doing (dead, teleporting, in base, jungle or lane farming, pushing, travelling) as `PlayerActivitySegmentDomain`; since analysis version 2 enemy siege creeps (`npc_dota_*guys_siege`, no `creep_` in the name, classified by `CreepClass`) count as lane farm. `CreepKillAnalyzer` stores `creep_kill` rows from the combat log and skips a match whose blob is codec version 1 (written before the gold and XP reasons were kept) until it is parsed again.
- **Draft board** (Ability Draft only; All Pick has no hero-pick recorder yet, so its board stays empty). `HeroDraftReader` (a `PoolDraftReader` sibling of `AbilityDraftReader`, one `DraftReaderFactory<HeroDraftFacts>` bean per mode; a mode reusing an existing part adds only a factory bean, but a new kind of draft part also needs a `ReplayFacts` field and one more reader slot in `ClarityReplayParser`, a known limit) reads `m_AbilityDraftHeroes` from the game rules like the skill pool and adds `ReplayFacts.heroDraft`; the readers stop looking at the game rules once all picks are seen or the game reaches pre-game, and the field name is built once per path for both; `HeroDraftExtractor` (`hero-draft`) writes `hero_draft_pick`: 12 rows per match (pool index, hero id, and for a picked hero its slot, team, turn 1 to 50, tick and clock seconds, negative before the horn; the 2 unpicked heroes keep null slot, turn, tick and clock). `ability_draft_pick` gains nullable `turnNumber` and `clockSeconds` (the skill and hero turns are one list of 50, merged by tick in `DraftTimeline`; both extractors check the draft shape through `DraftShape`, so an invalid hero draft leaves no hero rows and no skill turn or clock; `HeroDraftExtractor` keeps the old rows until a valid draft replaces them). `DraftBoardSection` (`draft-board`, order 11, off by default, `REPLAY_REPORT_SECTIONS_DRAFTBOARD_ENABLED`) shows hero picks in turn order, skills grouped by picker and what was left; hero and skill names go through `ReportHeroNames.heroName` and `AbilityLabels`, the one place to add icons. **Stored matches have no `hero_draft_pick` rows and no turn numbers until they are parsed again:** the facts come from the replay, so the only way is to bump `replay.processing.parser-version` (`REPLAY_PROCESSING_PARSER_VERSION`), which makes every finished match without a run of that version eligible again (`ReplayParseRunDomain` is unique per match and parser version, so the old run rows stay). Matches mapped within 24 hours are taken by the normal lanes, older ones only while `replay.processing.backlog.enabled` is on, and a match whose replay file Valve no longer serves ends with a failed run instead of new rows. A bump re-runs every extractor and analyzer for those matches, so do it only on purpose.
- **Player roles** (`PlayerRoleAnalyzer`, `@Order(15)`: after the activity, before the fights, deaths and outliers, which do not read roles yet) store one `player_role` row per player (role 1 carry, 2 mid, 3 offlane, 4 roaming or jungle support, 5 hard support; `source` `ASSIGNED` or `DERIVED`; confidence 0 to 1; evidence text; `analysisVersion`). The analyzer reads OpenDota's statistics and net worth series and the stored activity, takes the mode from `StoredMatchModes` and hands each team to the `RoleResolver` bean that `supports(mode)`; `supports(mode)` on the analyzer is true only when some resolver does, so a mode without one is skipped and writes nothing (All Pick and Ability Draft have one). A resolver also declares the `RoleStage`s it produces (`INTENT`: the picked hero and the skills he holds; `FINAL`: what he did) and is asked once per stage with a `RoleContext`; the final role goes to `player_role` as before (no stage column there), and every stage also goes to `player_role_profile` (unique on match, slot, stage): the role, confidence, evidence, and a `FunctionProfile` of nine 0 to 1 functions (farm priority, jungle, roaming, vision duty, initiation, disable, save and heal, damage, durability, plus the lane), null when nothing known tells it, and the five `roleScores` with `fitRole`, the best role by those scores alone (it may differ from `role`, which is the resolver's, so a disagreement between the two is explicit). A new mode adds a `RoleResolver` bean (and `requires()` for its extractors) with no edit in the analyzer; the analyzer loads the drafted skills of each player only when a resolver asks for `INTENT`. `AllPickRoleResolver` produces `FINAL` only, so All Pick gets no intent rows, and its profile rows repeat its role. `IntentProfileCalculator` reads a profile off a `HeroConstant` and the `AbilityConstant`s of the held skills (the ultimate counts 1.5; disables, gap closers, saves come from attribute keys, since the constants have no flags; `IntentStageProfiler` does the lookup through `HeroKits`); `ObservedProfiler` reads the final profile from the net worth place, lane role and laning activity, and leaves vision duty, initiation, disable, save and heal, damage and durability null until their data reaches the analyzer; `RoleFitter` scores a profile against each role and gives a team one role each through `RoleAssignmentSolver`. `ReplayAnalyzer.requires(mode)` (default: `requires()`) is what `ReplayAnalysisService` checks, so `PlayerRoleAnalyzer` names `activity` plus the `requires()` of the resolver of that match's mode only: a failed `ability-draft` extractor makes the Ability Draft roles unavailable (and what reads them), never the All Pick ones. If a resolver leaves a team slot without a role or names a slot outside the team, that slot gets no profile row (one INFO line) and the roles are still stored. Every weight, scale and key list of the profiles and the fitter is in `RoleProfileProperties` (`replay.analysis.role-profile.*`) and is a hypothesis for the learning loop. `AbilityDraftRoleResolver` (mode 18, requires `ability-draft`, stages `INTENT` and `FINAL`) is the first hypothesis resolver: each stage takes the profiles of its `StageProfiler` (looked up through `StageProfilers`: `IntentStageProfiler` from the hero and the drafted skills, `ObservedProfiler` from the match, the same observed inputs All Pick reads through the shared `NetWorthRanks` and `LaningActivity`) and fits them with `RoleFitter`, so each team gets each role once; the evidence names the stage and the three best roles by score, and an INTENT stage with nothing known (no draft stored) writes no rows (one INFO line). `RoleOverrides` (implemented by `RoleOverrideFile`, `replay/role-overrides.json`, path in `replay.analysis.role-overrides.resource`) holds what the constants cannot express: per skill name and per hero id, function values in (0, 1] named by `RoleFunction` (for example Axe's Berserker's Call is DISABLE and INITIATION, Teleportation is ROAMING, Borrowed Time is SAVE_HEAL); `IntentProfileCalculator` adds them to the rule-derived values before the cut at 1 (a skill's value times the skill or ultimate weight; a function the rules leave unknown becomes known), and a drafted skill the constants lack still counts when it has an override. The file is read and validated when the application starts: an unknown function, an ability name that is not lower snake case, a hero id that is not a number, a value outside (0, 1], an empty entry, an unknown section or a duplicated key stop it with the entry named. The FINAL stage knows only farm priority, lane, jungle and roaming for now (see `ObservedProfiler`), so Ability Draft final roles follow net worth and lane; the intent confidence is low by construction (small margins). The weights are first guesses for the loop. `AllPickRoleResolver` (mode 22) scores each player against each role from his lane role (`lane_role`; OpenDota's `is_roaming` is not stored), his laning-phase time in mid, jungle and lanes other than his main one (from `PlayerActivitySegment`, up to `phase-lane-end-minutes`), and his net worth place in the team, final and at the end of the laning phase; `RoleAssignmentSolver` then tries every assignment so that each team gets each role once, a tie going to the first in role order. Confidence is how much the team's total score drops if the player must take any other role, up to 2 points for 1.0. The analyzer names `activity` in `requires()`, and `ReplayAnalysisService` counts an analyzer that failed or was skipped as unavailable for later ones that name it, so a failed activity run keeps the old role rows; a net worth series with a gap takes the latest earlier value, and a player without one is ranked on his final worth only, with half the confidence; a team whose stored slots are not exactly 0-4 or 128-132 gets no roles. The phase summaries run later (`@Order(50)`) and are not used. Round 2 rules (hypotheses, `RoleProfileProperties`): a skill whose attribute keys are in `attack-damage-keys`, that is an `Attack Modifier`, or a passive that deals damage adds `attack-skill-damage` to damage and `attack-skill-farm` to farm priority; a stun, hex, root, sleep, fear, taunt or silence of at least `initiation-min-control` seconds on a skill that reaches `initiation-min-cast-range` or hits an area adds `initiation-skill` to initiation whatever its cooldown; a skill with a key of `save-keys` counts as a save when it targets a friendly unit or has no target; and in the FINAL stage of `AbilityDraftRoleResolver` (`RoleResolver.scoredAs`, so All Pick scores are untouched) the lane bonus is multiplied by `fit.final-lane-factor` and an unknown function counts `fit.final-unknown-value` instead of `fit.unknown-value`. Known limits, not calibrated yet: the scoring weights, the roaming definition (time in lanes other than his main one, threshold 0.5) and what confidence means (a score margin, not a probability) are first guesses checked on two matches only. Real-data check: `PlayerRoleReplayTest` and, for Ability Draft with intent, final and composition rows in PostgreSQL, `ReplayPostgresSmokeTest` (replayTest; it also needs `constants-heroes.json`, `constants-abilities.json` and `constants-ability-ids.json` from OpenDota's `/constants` in the fixture directory, else the kits are empty).
- **Team composition** (`TeamCompositionAnalyzer`, `@Order(16)`, requires `roles`) reads the stored `player_role_profile` rows (the FINAL row's role is the final role; a repeated slot keeps the last row, one INFO line says what was dropped) and writes one `team_composition` row per team and stage (unique on match, team, stage; replaced per match): `PICK` from the INTENT profiles and `FINAL` from the FINAL profiles, each only when the team has all five, so All Pick writes `FINAL` only and Ability Draft both (the `PICK` verdict is judged on the intent profiles of `AbilityDraftRoleResolver`; `CompositionSection` shows what each tracked player was meant to play and played, and both verdicts). A row has the comma separated `tokens`, a plain-words `summary` (both cut to their column length) and the version; the wording of tokens and functions lives on `CompositionToken` and `RoleFunction`. The `CompositionRules` bean whose `supports(mode)` is true judges the team (`DefaultCompositionRules` serves All Pick and Ability Draft; a mode with its own rules adds a bean and the analyzer does not change). Tokens: `CARRIES_n` and `SUPPORTS_n` (counted from farm priority, only when 0 or at least the noted-from count), `NO_INITIATOR`, `NO_DISABLE`, `NO_WAVECLEAR` (judged on damage), `NO_FRONTLINE` (judged on durability), `NO_SAVE_HEAL`, `NO_VISION_DUTY` (FINAL only), `NO_FARM_ENGINE`, `TOP_HEAVY`, and `INTENT_NOT_PLAYED` (FINAL only, when the INTENT rows exist and the roles differ). A token that needs a function is never raised from a null: when no player known to have it reaches the threshold and some profile is null, the function is named under "Unknown" in the summary instead (All Pick FINAL profiles know only the farm priority and lane today, so most functions are unknown there). All thresholds are in `CompositionProperties` (`replay.analysis.composition.*`), hypotheses for the loop. `CompositionSection` (order 12, STANDARD detail, all modes) prints per tracked player "was meant to play X and played Y" (All Pick: "played Y") and the PICK and FINAL summaries of the tracked players' teams, nothing when no row is stored, each team line capped at `replay.report.max-composition-line-length`; the message caps are the report service's.
- **Fights are found from the stored combat log** (`FightAnalyzer`, after `ActivityAnalyzer` by `@Order`). `FightDetector` clusters hero-to-hero damage bursts and hero deaths; `FightAssessor` places the fight, picks a winner by the levels of the heroes killed (then by damage) and says for each of the ten players whether they were `ACTIVE`, `PRESENT_PASSIVE` or absent and why. A living hero who is away gets an `AbsenceReason` from his `HeroStateTimeline`: `NO_TP`, `TP_ON_COOLDOWN` (with the seconds left) or `HAD_TP_NOT_USED`, counting a TP scroll or Travel Boots. Heroes taking part are also ranked by how far toward the enemy they stood at the start (`FrontlineRanker`, rank 1 in front) and compared with the order their attack ranges suggest, short range in front: `frontlineDelta` is negative for a hero further forward than his range suggests. The attack range comes from the track (`attackRange`, as the game reports it; whether item and talent bonuses are in it is not verified), loaded with the rest by `PlayerTraces`; tracks stored before it existed get a rank but no delta. The three types are TEAMFIGHT (3 or more deaths, as OpenDota counts), SKIRMISH (1-2) and ENGAGEMENT (none, both sides hit hard). Tuning is in `ReplayAnalysisProperties` (`replay.analysis.fight-*`).
- **What each fighter did with his abilities** (`FightAbilityAnalyzer`, after `FightAnalyzer`): for each hero who took part, every learned ability and held item that is meant to be used (seen on cooldown, with a mana cost, or used at some point; passives are left out) gets a `FightAbilityUseDomain` row with its casts, damage to heroes and, when not cast, a `NonCastReason` (`ON_COOLDOWN`, `NO_MANA`, `DEAD_EARLY`, `READY_NOT_CAST`; range and target are not checked) and whether the last cast before the fight hit only creeps. Mana at the start comes from the track's absolute `mana`, so replays stored before it existed get no `NO_MANA`.
- **What heroes hold and can cast is stored as changes** (`ReplayStateChangeDomain`, by `StateRecorder` on the same 5-second grid): items gained and lost (counted by name), cooldowns starting, skill level-ups and mana costs (`MANA_COST`, which follows the skill level; the track also stores absolute `mana`). A hero item or ability's `m_fCooldown` is the time *remaining*, so a cooldown change carries the exact second it ends; its `m_flCooldownLength` may be 0 for some abilities. Together with the combat log's ability and item uses this answers "was it ready".
- **Every hero death gets an explanation** (`DeathAnalyzer`, after `FightAnalyzer`): `DeathAssessor` combines the track (where, who was near), the combat log (killer, damage and disables in the last 8 s, spell-immunity windows) and `HeroStateTimeline` (items held and cooldowns, rebuilt from the stored state changes) into a `DeathReason`. The combat log records an Aegis use as a death; the hero being alive again within 5 s marks it `REINCARNATED`, so the other deaths equal OpenDota's; a hero back within a walk of where he died, with no buyback after that death, is an Aegis, and one back at his fountain is not. `BuybackAnalyzer` (after the deaths) stores each buyback with the death it followed, how long he was dead and whether his team won that fight; the combat log's BUYBACK `value` is the player index 0-9. A disable counts only until its modifier was removed (a dispel or BKB ends it early), and one that took hold while spell immunity was on is recorded in `immunityPiercedBy` and makes the death `BKB_PIERCED` instead of `DIED_IMMUNE`; the modifier is named, not the ability that cast it. A death inside a fight carries that fight's `frontlineDelta` for the hero, and standing `replay.analysis.death-out-of-position-ranks` (2) or more places further forward than his attack range suggests, with no sharper cause, is `OUT_OF_POSITION`. `NO_BKB` (killed by a hero, no BKB owned, nothing sharper) applies only from `replay.analysis.death-no-bkb-min-seconds` (720) on, a time gate only because the assessor has no net worth; earlier deaths are `OTHER`. `DeathAnalysisDomain` is matched to OpenDota's `DeathEventDomain` by player and time, not by index.
- **Team states** (`TeamStateAnalyzer`, after the buybacks): from the per-minute net worth OpenDota stores for every player (it needs no replay data, but like the other analyzers runs after a replay was read), `TeamStateSegmenter` splits the game for each team into `AHEAD`, `EVEN` and `BEHIND` stretches (`GameStateSegmentDomain`). A lead of `replay.analysis.team-ahead-percent` (5) of both nets worth together must hold for 120 s to enter a state and a state is left only after the lead has been below half of that for 60 s, so a wobbling lead does not flap. A match without a complete net worth timeline gets no segments.
- **Buildings** (`BuildingKillAnalyzer`, after the fights): each fallen tower, barracks and ancient gets a `BuildingKillContextDomain` row (kind, tier, lane, owner, killer and whether it was a deny from OpenDota's objectives, the attacking heroes within 1500 units in the ten seconds before from the tracks and the frozen map, and the fight). The combat log has no killer, and its barracks and fourth-tower names differ from the map's (`MapLayout.buildingPosition` translates them). `MatchMapLayout` gives an analyzer the frozen layout of a match's map version.
- **Phases** (`PhaseSummaryAnalyzer`, last): for each player and phase (laning to minute 12, mid game to 25, then late game; `replay.analysis.phase-*`) a `PlayerPhaseSummaryDomain` row with the seconds in each activity (and the seconds with none recorded, so the columns add up to the phase), kills, deaths and assists from the per-minute counters, gold and experience per minute from OpenDota's series, and the fights that began in the phase while he was alive and those he took part in.
- **Swings** (`SpikeAnalyzer`, after the phases): `SpikeDetector` finds the stretches in which the net worth difference between the teams moved by at least 1500 and 3% of both teams' together within 3 minutes and goes on while it keeps moving; one that turns a lead of 1000 or more into the other team's is a change of direction (`GameSpikeDomain`). Each swing gets evidence rows (`GameSpikeFactorDomain`): the gold sources that moved (hero kills, farm, buildings, Roshan, bounty, comeback gold, what the other team spent on buybacks) from the per-minute counters, and the fights, buildings and buybacks inside it. The primary cause is the source with the biggest share of the swing, at least 10%, named `FIGHT_WIN` (hero kills with a fight the favoured team won in the window), `PICKOFF`, `OBJECTIVE`, `ROSHAN_AEGIS`, `BUYBACK_SWING`, `CARRY_FARM`, `COMEBACK_GOLD` or `OTHER`. Net worth comes from OpenDota (`TeamNetWorth`); without the replay's counters a swing is `OTHER`. Key item (`KeyItemFinder`, `replay.analysis.spike.key-item-window-seconds` 240 and `key-item-min-cost` 2000): one `ITEM` row per swing, the most expensive item a hero of the favoured team first got (replay item state changes, not OpenDota's purchase log, which an unparsed match lacks) in the window before the swing, bought before its first fight, by a hero ACTIVE in one of its fights; no such item, no row. A gain is skipped when a teammate lost the same item within 60 s (trade, drop), for recipes, for names in `key-item-excluded` (shards, wards, consumables; trailing `*` is a wildcard), and for a higher tier (`_2` to `_5`) when the hero held a lower one; a sale and rebuy more than 60 s apart counts again; a lower tier a teammate held is not checked (known limit). The ITEM row stays in the factor table, with the fight lead of 30 s as the fights' anchor; readers ignore factor types they do not know. Not done: feeding, and the outliers of the plan.
- **Outliers** (`OutlierAnalyzer`, after the swings): from the per-minute net worth, a player holding more than `replay.analysis.outlier-share-percent` (35) of his team's for 3 minutes while joining fewer fights than the team median is a `NW_OUTLIER`, and one holding less than 10% for 5 minutes with at least 5 deaths and more than twice the team's median is a `FEEDER` (`PlayerOutlierDomain`, with his place by fights joined). Analysis version 2 adds why, as nullable columns: `incomeBreakSeconds` (the first minute of the first stretch of `replay.analysis.income-break-minutes` (3, 1 to 30) in a row, touching the outlier stretch, in which his net worth gain per minute differed from his teammates' average by at least `income-break-share` (0.25, above 0 to 5) of that average, up for an outlier and down for a feeder; null without one or without teammates; validated at start-up, NaN included), `mainIncomeSource` (`IncomeSource`: lane creeps, jungle creeps, kills and assists, buildings, bounties and other gold, the largest gain of the minute counters of `replay_player_minute` from the break to the end of the stretch; passive income, shared and reliable gold are not told apart; null without counters) and `explanation` (one plain sentence of at most 400 characters from `OutlierWording`, naming no hero: the income break and source, the fights joined against the team median, and for a feeder the deaths in the stretch and the commonest reason). The analyzer still names nothing in `requires()`: the outliers come from OpenDota's net worth, and a missing minute or death row only turns the explanation parts null (no source without a break; death reasons without wording are counted but never named, a tie goes to the first reason alphabetically). Of the stretches overlapping the outlier window, the break is the one that starts latest; the source is measured from the later of the break and the window start. Rows written before version 2 keep null columns until `reanalyze` runs. Team rotations run later (`@Order(90)`), so the wasted-rotation count is added by `OutliersSection` at read time, not stored. The `outliers` analysis section (`OutliersSectionReader`, order 75) lists the rows; in Discord `OutliersSection` (`outliers`, STANDARD, order 78, **default off**, up to `replay.report.max-outlier-lines` (4, 1 to 10), lines like "Sven held 41% of the net worth of Radiant from 24:00 (his income rose from minute 20 and came mostly from jungle creeps; he joined 3 of 11 fights, fewer than the team median of 7)").
- **Reasons** (`FightReasonAnalyzer`, `@Order(32)`, after the fight, ability and death analyzers): per fight, every `ReasonContributor` that `supports(mode)` adds `Reason`s (code, player or team, severity 0 to 1, evidence, source `COMMON` or the mode) to `fight_reason`, all kept (no cap; the top-3 belongs to the report). The common contributors (`AbsenceReasonContributor`, `AbilityNonCastReasonContributor`, `DeathReasonContributor`) only mirror the old columns; the role-aware common contributors read `player_role` and `team_composition` through `FightContext` and stay quiet without them: `CarryFarmingElsewhereContributor` (final role 1 or 2, absent, `activityAtStart` jungle or lane farm), `SupportAbsentContributor` (roles 4 and 5, absent and not dead), `RoleGapContributor` (the losing team's FINAL composition tokens that name a function, as TEAM reasons coded by the token); weights by role and presence only, never gold. A mode adds a contributor bean and the analyzer does not change; the mode contributors (`ModeReasonContributor`, source `ABILITY_DRAFT` or `ALL_PICK`) read the INTENT/FINAL profiles, hero ids and pool through `FightContext`: `INTENT_NOT_PLAYED`, `WEAK_COMBINATION` (the losing team's best INTENT value below a bar in several of initiation, disable, damage, with enough profiled players) and `STRONG_SKILL_LEFT` (off by default, `replay.analysis.reasons.strong-skill-left.enabled`, until the single-skill scoring is fixed) for Ability Draft, `HERO_ROLE_MISMATCH` (hero tags of the constants against the final role) for All Pick. Severities are first-guess hypotheses in `ReasonProperties` (`replay.analysis.reasons.*`).
- **Late reasons** (`LateFightReasonAnalyzer`, `name` `late-fight-reasons`, `@Order(95)`, requires `fights`, `fight-reasons`, `fight-loss`, since it edits `fight_explanation.reason_count`; it does not require the vision or rotation tables, a contributor with no rows of its own adds nothing, so one failed analyzer does not cost the other's reasons): the vision (80) and rotation (90) tables do not exist when `FightReasonAnalyzer` (32) runs and those analyzers do not move, so a second pass appends to `fight_reason` after the objective analyzer (94) from `LateReasonContributor` beans (sibling of `ReasonContributor`, reading a `LateFightContext` = the `FightContext` plus `fight_vision` rows and `team_rotation`; `FightContextLoader` and `FightReasonRows` are shared with the first pass). It replaces only the rows of its contributors' `source` (`VISION`, `ROTATION`), so a re-run is idempotent and first-pass rows stay; `FightReasonAnalyzer`'s first pass deletes all rows of the match, late ones included, so the full pipeline order (late pass after it) is required, and a single-analyzer re-run of `fight-reasons` needs the late pass run again. Readers rank `fight_reason` on read, so the rows compete through `ReasonRanking` like the rest; `fight_explanation.reason_count` (written by `FightLossAnalyzer` at 70) is recounted by the second pass (`ReasonRanking.countOfTeam`). `VisionReasonContributor` (important fights only, team reasons of the losing team): `NO_VISION_BEFORE_FIGHT` only when the winner's row had vision, `NO_DETECTION_VS_INVISIBLE`, weak `LATE_WARD`. `RotationReasonContributor`: `ROTATION_WASTED_BEFORE_FIGHT` and `ROTATION_DIED_BEFORE_FIGHT` (player, by verdict) for a rotation of a losing-team hero that ended within `replay.analysis.reasons.rotation-window-seconds` (60) before the fight or overlapped it, when he was absent from it (no fight row or not ACTIVE or PRESENT_PASSIVE; a passive hero is left out, he did not miss the fight). `NO_VISION_BEFORE_FIGHT` needs the winner's `activeObservers` known and above zero. Left as is: the second pass reloads the full `FightContext` (performance only), and the severities are first guesses; a vision team reason can outrank draft-level reasons, which always rank last. Severities `vision-severity` and `rotation-severity` are validated at startup.
- **Lost fights** (`FightLossAnalyzer`, `@Order(70)`, after the spikes): `fight_explanation` per fight with a decided winner (loser, swing, gold the loser's deaths cost, count of the loser's reasons, zero kept); storage is uncapped, `ReasonRanking` orders reasons on read (severity, team reasons below player reasons unless no player reason reaches `replay.analysis.fight-loss.min-player-severity`; one entry per hero for the absence family with the others as `also`; draft-level reasons last; cooldown reasons unranked before `early-fight-seconds`), and `FightExplanationReader.read(matchId, topReasons, maxFightsPerSwing)` is the read model the report caps (3 and 2): `SwingSection` adds a line per lost fight under its swing (`ReasonWording` words each reason by code; caps `replay.report.max-reasons-per-fight` and `max-lost-fights-per-swing`). Reviewed with `:server:reviewLoop -Ploop.topic=fights` (`docs/replay-fight-loop/README.md`).
- **Important fights** (`ImportantFightAnalyzer`, `@Order(75)`, after `fight-loss`): `fight_importance` per decided fight from OpenDota's per-minute gold and XP advantage (`TeamTimelineDomain`) and the teams' net worth (`AdvantageSeriesReader`); important when the winner's gold advantage grew over the fight plus a 60 s lag by 3% of its net worth or 1500 gold, or the lead flipped to the winner (`replay.analysis.important-fights.*`; XP and slope breaks never decide). `FightExplanationReader.read` and so the ranking and the Discord line use only important fights, `readAll` and the fights loop list all; reasons stay stored for every fight. See `docs/replay-fight-loop/README.md`.
- **Runes and the opening** (`RunePickupAnalyzer`, `runes`, `@Order(14)`): `rune_pickup` per rune taken (zone from the track, the taker's bounty gold, a mid lane proxy) and `opening_summary` per team (window -30 s to +90 s around the first spawn, gold plus XP balance, kills break a tie; needs a v2 combat log). `RuneAdvantageReasonContributor` adds `RUNE_ADVANTAGE` and `ENEMY_RUNE_ADVANTAGE` for a power rune active in a fight; `ModifierWhitelist` keeps `modifier_rune_*`. Loop topic `runes`, see `docs/replay-rune-loop/README.md`.
- **Item efficiency** (`ReplayItemEfficiencyAnalyzer`, `@Order(85)`; not the OpenDota based `ItemEfficiencyAnalyzer` of the match report): `item_efficiency` per hero and entry of the whitelist `replay/item-efficiency.json` (Magic Stick and Wand, Hand of Midas, the farming group Battle Fury, Maelstrom, Mjollnir), judged by one `ItemEfficiencyEvaluator` bean per `kind`; a new item is a JSON entry, a new kind one evaluator class. Loop topic `items`, see `docs/replay-item-loop/README.md`.
- **Items section** (`ItemsSection`, `items`, STANDARD, order 77, **default off**; reads `item_efficiency` only): up to `replay.report.max-item-lines` (4, 1 to 10) short verdict-first sentences (hero, item display name, bought at m:ss or 'at the start' before the horn), tracked players' rows first, then the rows furthest from paying their cost; rows of an unknown kind are skipped quietly, rows missing figures with one WARN. Each kind is an `ItemKindWording` bean (`complete`, `longVerdict` for the item loop, `shortVerdict` for Discord) found through `ItemKindWordings`; `ItemWording` holds the shared phrases; section orders must be unique (tested).
- **Vision** (`VisionAnalyzer`, `@Order(80)`, after `important-fights`): `fight_vision`, one row per team for each important fight only, in the window 90 s before to 15 s after it (`replay.analysis.vision.*`): own observers and sentries covering the fight when it began (within their radius plus 620 units of a hero in it) (ward cells converted by `WardCoordinates`), a late ward flag, enemy wards destroyed, the enemy's invisible heroes (game invisibility modifier, plus `replay/invisible-heroes.json`), the team's detection and a verdict (`NO_VISION`, `INVISIBLE_HERO_NO_DETECTION`, `LATE_WARD`, `FINE`). Not part of `fight_reason`; the Discord `vision` section (`VisionSection`, `vision`, STANDARD, order 76, **default off**) reports `NO_VISION` only as a contrast (the other team in the fight had wards; fights where neither had are not lines, one sentence when that is most fights), `INVISIBLE_HERO_NO_DETECTION` and `LATE_WARD` as stored, one line per fight and team (the tracked team's first, else both, the view says which), at most `replay.report.max-vision-lines` (4, 1 to 10) chosen by the absolute net worth swing, then the tracked team, then the worse problem, with a summary first (omitted when 0) and 'and N more'; wording in `VisionWording`. Known limit: towers and nearby heroes are not vision, so 'no vision' means no ward. See `docs/replay-vision-loop/README.md`.
- **Team rotations** (`BehaviourRotationAnalyzer`, `rotations`, `@Order(90)`, `replay.analysis.behaviour.*`): `team_rotation` per hero trip away from the team's biggest group of living heroes (2500 units, away 20 s, jungle farming is not away, a death or buyback ends it) that got to another lane and came to something; verdict GOOD, WASTED (lost lane proxy, or did nothing while income dropped, or own tower lost; B1b, v2 stores `reasons` and income per minute), DIED or NEUTRAL; review loop topic `behaviour` (`docs/replay-behaviour-loop/README.md`), nothing in Discord.
- **Group or split and lane swap** (`BehaviourSplitAnalyzer` `team-splits` `@Order(91)`, `BehaviourLaneSwapAnalyzer` `lane-swaps` `@Order(92)`): `team_split_stretch` (per team, stretches of GROUPED, SPLIT or MIXED after the last lane pair ended, fallback 12:00, min 2 minutes, with towers lost and taken, heroes lost and kills) and `team_lane_swap` (stored lane against the lane stood in most of minutes 8 to 12); shown as two more tables of the `behaviour` loop topic, nothing in Discord.
- **Smoke use** (`BehaviourSmokeAnalyzer`, `smoke`, `@Order(93)`; requires `players`, `tracks`, `combat-log`, `deaths`, `building-kills`): `smoke_use`, one row per `item_smoke_of_deceit` use with a `modifier_smoke_of_deceit` on the user (group = same-team heroes that got the modifier within `smoke-group-seconds`; end = first modifier removed before its full duration, else the last one running out; outcome PAID_OFF, NOTHING or BACKFIRED from what the group did until `smoke-outcome-seconds` (20) after the end); a seventh table of the `behaviour` loop topic, nothing in Discord.
- **Objectives after a fight** (`BehaviourObjectiveAnalyzer`, `objectives`, `@Order(94)`; requires `important-fights`, `fights`, `building-kills`, `combat-log`, `tracks`, `team-state`, `players`): `objective_conversion`, one row per important won fight: CONVERTED (enemy tower, barracks, ancient or Roshan by the winner within `objective-window-seconds` (90) of the fight's end) or MISSED with the nearest enemy tower still standing and the distance of the winner's closest hero; Roshan rows say who stood at the pit and whether it was expected (ahead) or a gamble (behind); an eighth table of the `behaviour` loop topic; in Discord only `ObjectivesSection` (`objectives`, STANDARD, order 74, **default off**): a summary "Won fights turned into objectives: X of Y", up to `max-objective-lines` (3, 1 to 10) MISSED lines (biggest gold swing from `fight_importance`, else the most recent; the nearest tower and the closest hero as close, a fair way or far by `objective-close-distance` 1500 and `objective-far-distance` 4000; the window is `replay.analysis.behaviour.objective-window-seconds`) and one Roshan sentence, shared words in `ObjectiveWording`. The window comes from the row's `windowSeconds` (rows from before version 2 say "soon after"); "and N more missed fights" counts what the cap left out; a fight without a clock ranks oldest and never gets the Roshan sentence. Known limit: the close and far cut-offs are the current config, not the one a row was stored under.
- **The replay analysis reaches Discord as a follow-up in the match thread** (`ReplayReportService`, off until `replay.report.enabled`): the orchestrator stores each channel's thread (`MatchReportThreadDomain`, deleted with the match) when it creates it, and `ReplayBatchService` calls `deliver(matchId)` as soon as a match's run ends `DONE`, or `PARTIAL` with no retry left (`deliverFinished`); after each batch `ReplayProcessingJob` still calls `deliverPending` as a catch-up for what had to wait, which looks at `DONE` runs and final `PARTIAL` runs that finished in the last `lookback-hours` and, for each active channel tracking a player of the match, posts once (`ReplayReportPostedDomain`). It skips a channel that turned `replay_report` off, asked for `MINIMAL` detail, is in its quiet hours (it is tried again on the next run) or has no stored thread (a match reported before this existed is never followed up). A `ReplayReportSection` bean writes one part (`SwingSection`, `DeathSection` for the deaths worth explaining of the tracked players, `FightSection` at FULL detail for big fights they could not join and abilities left ready in several fights, `MovementSection` at FULL for where each phase's time went and the fights joined, and `DraftSection` for what they drafted, Ability Draft only) from the stored tables; the text goes out through the existing `TextReport` formatting, capped at `max-messages` (4 at FULL, `standard-max-messages` 2 otherwise) with the left-out count stated. Each section has a unique `name()` (`swing`, `deaths`, `fights`, `movement`, `draft`, `composition`) and `SectionSwitch` reads `replay.report.sections.<name>.enabled` on every post; when unset the section follows `defaultEnabled()` (false in the interface, so a new section ships off until the owner accepts its table and the config turns it on; the six existing sections override it to true). A property for an unknown section name, or a duplicate section name, fails start-up listing the known sections. `ImportantFightsSection` (`important-fights`, STANDARD, order 65, **default off**) lists the important fights of the match, one line each (time, winner, net worth swing, lead flip, top 2 reasons), the costliest `replay.report.max-important-fight-lines` (6, must be 1 to 15) in time order; every listed fight prints its own top reasons, so it repeats fights `SwingSection` also explains (sections stay independent; the owner enables whichever reads better). `LanesSection` (`lanes`, STANDARD, order 20, **default off**) tells each lane in one line (winner with '(your team)', margin in words from `replay.report.lane-clear-margin` 0.3 and `lane-big-margin` 0.6, heroes, m:ss, top 2 reasons, level 6 note), cut at `max-lane-line-length` (400, 60 to 600); wording in `LaneWording`, shared with the lane loop; known limit: the level 6 note reads the level from `LaneProperties` as configured now, not as stored. `RotationsSection` (`rotations`, STANDARD, order 70, **default off**) lists up to `max-rotation-lines` (4, 1 to 10) `team_rotation` rows, DIED first, then WASTED (both earliest first when the cap bites), then the GOOD ones with most kills and won fights (neutral never), in time order, with the loop's why sentences, what a good trip won, or "No reason recorded"; `SmokeSection` (`smoke`, STANDARD, order 72, **default off**) lists up to `max-smoke-lines` (3, 1 to 10) `smoke_use` rows (paid off or backfired, then came to nothing, then no known outcome; an unreadable group says "a group that is not known", never alone), nothing without smoke; both cut at `max-behaviour-line-length` (400, 60 to 600); `OpeningSection` (`opening`, STANDARD, order 18, **default off**) is up to three lines under a header from `opening_summary` and `rune_pickup`: who won the opening and by how much (gold and XP, kills break a tie, '(your team)'), the bounty runes per team with their gold in total and who took the first, and the power and water runes taken in the mid lane; nothing without an `opening_summary`; the mid lane runes are those of the first `opening-rune-minutes` (10, 1 to 30); cut at `max-opening-line-length` (400, 60 to 600); pickups with an unresolved team are left out of the bounty count and the `midLane` flag stays a proxy; wording in `OpeningWording`, shared with the rune loop; wording in `BehaviourWording`, shared with the behaviour loop, whose creep count now prints "?" instead of "null" for a null count; the smoke test writes the rendered sections into `~/dbuff-fixtures/send`; times before the horn print negative (`-1:00`).
- **End game and throw** (`EndGameAnalyzer`, `end-game`, `@Order(96)`; requires only `fights`, version 2): `end_game_summary`, one row per match, replaced on every run; the importance, `objective_conversion` and buyback tables are soft inputs, so when they are empty the turning point, buybacks (0) or final fight degrade instead of skipping the match (unfrozen maps have no conversions). The winner comes from `MatchDomain.radiantWin` (no row without it, one INFO line). `leadKnown` says whether the per-minute net worth timeline was read: false is "not known" (the section says only who won), not "never led". The loser "led" only when its largest lead in gold reaches both `replay.analysis.end-game.min-lead-gold` (2000) and `min-lead-share` (0.03 of both teams' net worth together); `leadLost` = not leading at the last whole minute sample (which may be before the game ended) and `lastLeadGold` is that lead. `thrown` = a lead was found, was lost, and the loser held at least `throw-lead-share` (0.10) AND `throw-min-gold` (3000) in samples from `throw-min-minute` (10) on for at least `throw-min-seconds` (120; a minute sample counts 60 s), so an early or small lead is no throw. Turning point (only when the lead was lost): the winner's first won fight whose end is at or after the peak that is a CONVERTED `objective_conversion` row, else the winner's important fight with the same overlap rule and the largest `goldChange`. Buybacks per team in the last `buyback-window-seconds` (600) from `buyback_event`; final fight = last important fight, else last fight. Not computed: buyback readiness from gold (the data has net worth but not unspent gold). Reader section `endgame` (a list with one row, empty without a summary); Discord `EndGameSection` (`endgame`, STANDARD, order 79, **default off**): a verdict line (won / thrown / "although X still led by Nk at the last minute" / never led) and a buyback line (skipped when neither team bought back), each cut at `replay.report.max-end-game-line-length` (400, 60 to 600).

### REST API access

`ApiKeyFilter` requires `X-Api-Key` on everything except `/actuator/health` (exempt because the CI health gate and rollback poll it). The exemption is judged on the container-normalised servlet path, not `getRequestURI()`, which still carries `/../`. `app.api.required` is false locally, so an empty `DBUFF_API_KEY` runs open; the `prod` profile sets it true, so a missing key **closes** the API (every request 401) rather than opening it. The bot never calls the REST API, so closing it does not affect Discord features.

The key reaches the running host through `scripts/set-api-key.sh`, which stores it as an SSM SecureString and has the instance write a root-only systemd drop-in (`/etc/systemd/system/dbuff.service.d/api-key.conf`) — it survives JAR deploys. It is deliberately **not** added to the instance `UserData` in `template.yaml`: `UserData` only runs on first boot, so it would not reach the live server, and editing it makes the next `deploy.sh deploy` stop/start the instance. After a rebuild, run the script again. `scripts/lib/ssm.sh` holds `run_ssm`, shared by it and `deploy-release.sh`.

Port 8080 can be narrowed with `ALLOWED_API_CIDR` (`deploy.sh deploy`, an in-place security-group change); the bot needs no inbound access.

### Production Topology

A single `t4g.small` (Graviton/arm64) EC2 instance runs both the Spring Boot app
and PostgreSQL 16 on `localhost`, provisioned by
`infrastructure/cloudformation/template.yaml` in `eu-north-1`. There is no RDS
instance — it was removed to cut the bill roughly in half, since a dedicated
database and its second public IPv4 address together cost more than the compute.

Consequences worth knowing before changing anything here:

- **The instance is arm64.** Any native dependency must have an aarch64 build.
- **Backups are a nightly `pg_dump`** to `s3://dbuff-deploy-<account>/db-backups/`
  via the `dbuff-backup.timer` systemd timer (02:30 UTC). Trigger one on demand
  with `./infrastructure/cloudformation/deploy.sh backup-now`; restore with
  `... restore <key>`. Losing the instance without a backup loses the database —
  there is no longer a managed snapshot to fall back on.
- **RAM is the binding constraint** (~2 GiB shared between the JVM at `-Xmx512m`,
  Postgres at `shared_buffers=256MB`, and a 2 GiB swapfile as a safety net).

### Deploying

**Application code ships through CI.** A push to `main` runs
`.github/workflows/ci-cd.yml`: the `verify` job builds and tests, and the
`deploy` job installs the JAR that those tests passed, then gates on
`/actuator/health` and rolls back to the previous release if it does not come
up. Do not deploy application changes by hand — merge to `main` instead. CI
authenticates via GitHub OIDC (role from `infrastructure/cloudformation/cicd.yaml`,
a stack separate from `dbuff`), so there is no long-lived AWS key.

**Infrastructure stays manual, deliberately.** The `dbuff` stack owns the EC2
instance that hosts the database, so CI has no permission to touch it. Apply
template changes yourself:

```bash
./infrastructure/cloudformation/deploy.sh deploy   # apply template.yaml
./infrastructure/cloudformation/deploy.sh cicd     # apply cicd.yaml (CI identity)
./infrastructure/cloudformation/deploy.sh all      # build + upload + deploy, the pre-CI manual path
```

`build`/`upload`/`all` remain for emergencies and for bootstrapping a rebuilt
instance. Note that a stack update replacing the instance destroys the local
database — take a backup first.
